## 1. HTMLレンダリングとは

「レンダリング」という言葉は、ブラウザがHTMLを画面に描画することを指す場合もありますが、ここでは別の意味で使います。

本ワークショップでの「HTMLレンダリング」とは、**HTMLを生成する行為**のことです。

例えば、エディタでHTMLを手書きすることも、ある種のHTMLレンダリングと言えます。

### HTMLの生成方法は進化してきた

マークアップエンジニアの皆さんが普段やっている作業を振り返ってみましょう。

1. **手書き**: エディタで `<div>` や `<p>` を直接書く
2. **テンプレートエンジン**: EJS、Pugなどで共通パーツを管理しつつHTMLを生成する
3. **フレームワーク**: ReactやAstroがデータに基づいてHTMLを自動生成する

どの方法でも最終的にはHTMLが生まれますが、**「いつ」「どこで」HTMLが生成されるか**が異なります。この違いが、これから学ぶレンダリング手法の核心です。

## 2. 【復習】コードが動く場所

HTMLレンダリングを理解するために、まず「コードが動く3つの場所」を復習します。

```
┌──────────┐      ┌──────────┐      ┌──────────┐
│  開発者   │  →   │  サーバー  │  →   │  ユーザー  │
│  のPC     │      │          │      │ のブラウザ │
│          │      │          │      │          │
│ コードを  │      │ リクエスト │      │ HTMLを    │
│ 書く・    │      │ に応じて   │      │ 受け取り  │
│ ビルドする │      │ 処理する   │      │ 表示する   │
└──────────┘      └──────────┘      └──────────┘
```

### 開発者のPC

皆さんがコードを書いている環境です。エディタでHTMLやCSS、JavaScriptを書き、必要に応じてビルド（変換・結合・最適化）を行います。

ポイント：**この段階で完成したHTMLを生成してしまうこともできる**（後述するSSG）

### サーバー

Webサイトのデータを保管し、ユーザーからのリクエストに応じてレスポンスを返すコンピュータです。

ポイント：**リクエストのたびにHTMLを生成することもできる**（後述するSSR）

### ユーザーのブラウザ

ユーザーが実際にWebサイトを閲覧する環境です。サーバーから受け取ったHTML・CSS・JavaScriptを解釈して画面に表示します。

ポイント：**ブラウザ上でJavaScriptがHTMLを生成することもできる**（後述するCSR）

## 3. 3つのレンダリング手法

HTMLが「いつ」「どこで」生成されるかによって、3つの手法に分かれます。

| 手法 | いつ | どこで | 生成タイミング |
|---|---|---|---|
| **SSG** | ビルド時 | 開発者のPC | デプロイ前 |
| **SSR** | リクエスト時 | サーバー | ユーザーがアクセスするたび |
| **CSR** | 実行時 | ユーザーのブラウザ | ページ読み込み後 |

### SSG（Static Site Generation）

**ビルド時にHTMLを生成し、完成したHTMLファイルをサーバーに置く方式です。**

```
┌──────────┐              ┌──────────┐              ┌──────────┐
│  開発者   │              │  サーバー  │              │  ユーザー  │
│          │   デプロイ    │          │   リクエスト  │          │
│ ビルド →  │  ──────→    │ 完成した   │  ──────→    │ HTMLを    │
│ HTML生成  │   HTML配置   │ HTMLを    │   HTML配信   │ そのまま  │
│          │              │ 保管      │              │ 表示      │
└──────────┘              └──────────┘              └──────────┘
    ここで生成！
```

#### マークアップエンジニアにとって最も馴染み深い

実は、皆さんが普段やっている「HTMLを書いてサーバーにデプロイする」という作業は、手動のSSGとも言えます。SSGはこれを自動化したものです。

```
手動SSG（従来の制作フロー）:
  エディタでHTMLを書く → サーバーにデプロイ

自動SSG（フレームワーク利用）:
  コンポーネントを書く → ビルドコマンドでHTMLを生成 → サーバーにデプロイ
```

#### SSGに向いているサイト

- 企業のコーポレートサイト
- ブログ・メディアサイト
- ドキュメントサイト
- LP（ランディングページ）

**共通点**: コンテンツが頻繁には変わらない

#### SSGのメリット・デメリット

| メリット | デメリット |
|---|---|
| 表示が非常に速い（生成済みHTMLを返すだけ） | コンテンツ更新のたびにビルド＆デプロイが必要 |
| サーバーの負荷が低い | ユーザーごとに異なる内容を出しにくい |
| セキュリティリスクが低い | ページ数が膨大だとビルドに時間がかかる |

#### 代表的なフレームワーク

- **Astro** — 前回紹介。コンテンツサイトに最適
- **Next.js** — SSGモードあり（SSRも可能）
- **Gatsby** — React製のSSG特化フレームワーク

### SSR（Server Side Rendering）

**ユーザーがページにアクセスするたびに、サーバーがHTMLを生成して返す方式です。**

```
┌──────────┐              ┌──────────┐              ┌──────────┐
│  開発者   │              │  サーバー  │              │  ユーザー  │
│          │   デプロイ    │          │   リクエスト  │          │
│ テンプレー │  ──────→    │ リクエスト │  ←──────    │ ページを  │
│ トを書く  │   コード配置  │ を受けて   │   HTML返却   │ リクエスト │
│          │              │ HTML生成  │  ──────→    │          │
└──────────┘              └──────────┘              └──────────┘
                              ここで生成！
```

#### PHPの時代から使われてきた

SSRは実は古くからある手法です。PHPやRuby on Railsなど、サーバーサイドの言語でHTMLを生成する方式はすべてSSRです。

```php
<!-- PHP: リクエストのたびにHTMLを生成 -->
<?php
$user = getUserFromDB($_SESSION['user_id']);
?>
<html>
  <body>
    <h1>こんにちは、<?php echo $user->name; ?>さん</h1>
    <p>最終ログイン: <?php echo $user->last_login; ?></p>
  </body>
</html>
```

このPHPコードは、ユーザーがページにアクセスするたびに実行され、そのユーザー専用のHTMLを生成します。

#### SSRに向いているサイト

- ECサイト（ユーザーごとのカート、おすすめ商品）
- SNS（ログインユーザーごとのタイムライン）
- 管理画面（権限ごとに表示が変わる）
- リアルタイム性が求められるサイト（在庫状況、価格変動）

**共通点**: ユーザーやタイミングによって表示内容が変わる

#### SSRのメリット・デメリット

| メリット | デメリット |
|---|---|
| ユーザーごとに異なる内容を返せる | リクエストのたびにサーバーで処理が走る |
| 常に最新のデータを表示できる | サーバーの負荷が高くなりやすい |
| SEOに有利（完成したHTMLが返る） | サーバーが落ちるとサイト全体が表示できない |

#### 代表的なフレームワーク

- **Next.js** — ReactベースでSSRが得意
- **Nuxt.js** — VueベースのSSRフレームワーク
- **Ruby on Rails / Laravel / Django** — 伝統的なSSRフレームワーク

### CSR（Client Side Rendering）

**サーバーはほぼ空のHTMLを返し、ブラウザ上でJavaScriptがHTMLを生成する方式です。**

```
┌──────────┐              ┌──────────┐              ┌──────────┐
│  開発者   │              │  サーバー  │              │  ユーザー  │
│          │   デプロイ    │          │   リクエスト  │          │
│ JSを書く  │  ──────→    │ ほぼ空の  │  ──────→    │ JSが      │
│          │   JS配置     │ HTMLと    │   HTML+JS   │ HTMLを    │
│          │              │ JSを配信  │   配信       │ 生成して  │
└──────────┘              └──────────┘              │ 表示      │
                                                    └──────────┘
                                                    ここで生成！
```

#### サーバーが返すHTML

CSRでは、サーバーが返すHTMLは中身がほぼありません。

```html
<!-- サーバーが返すHTML -->
<!DOCTYPE html>
<html>
  <head>
    <title>My App</title>
  </head>
  <body>
    <div id="root"></div>          <!-- 中身は空！ -->
    <script src="/app.js"></script> <!-- このJSがHTMLを生成する -->
  </body>
</html>
```

ブラウザがこのHTMLを受け取ると、`app.js` が実行され、JavaScriptが `<div id="root">` の中にUIを構築します。

```jsx
// app.js（React）: ブラウザ上でHTMLを生成
function App() {
  const [todos, setTodos] = useState([]);

  return (
    <div>
      <h1>TODOリスト</h1>
      <ul>
        {todos.map(todo => <li key={todo.id}>{todo.text}</li>)}
      </ul>
    </div>
  );
}

// ↑ このコードがブラウザで実行され、DOMが構築される
```

#### CSRに向いているサイト

- Webアプリケーション（GmailやSlackのような）
- 管理ダッシュボード
- リアルタイムチャット
- インタラクティブなツール（デザインツール、エディタ）

**共通点**: ページ遷移なしに、頻繁にUIが変化する

#### CSRのメリット・デメリット

| メリット | デメリット |
|---|---|
| ページ遷移なしでUIが切り替わる（快適な操作感） | 初期表示が遅い（JSの読み込み・実行が必要） |
| サーバー負荷が低い（HTMLを生成しない） | SEOに不利（検索エンジンがJSを実行しないと中身が見えない） |
| リッチなインタラクションが可能 | JavaScriptが無効だと何も表示されない |

#### 代表的なフレームワーク

- **React**（Create React App） — CSRがデフォルト
- **Vue.js**（Vue CLI） — CSRがデフォルト
- **Angular** — CSRがデフォルト

## 4. すべての手法を理解する必要性

### 「マークアップエンジニアはSSGだけ知ればいい」のか？

答えは **No** です。理由は3つあります。

#### 1. プロジェクトのレンダリング手法を理解する必要がある

皆さんが参加するプロジェクトがSSRやCSRを採用している場合、HTMLの書き方や考え方が変わります。

| | SSG | SSR | CSR |
|---|---|---|---|
| HTMLを書く場所 | `.html` or テンプレート | サーバーサイドのテンプレート | JSXなどのコンポーネント |
| 動的な値の埋め込み | ビルド時に確定 | リクエスト時にサーバーで埋め込む | ブラウザで実行時に埋め込む |
| CSSの読み込み | `<link>` タグ | `<link>` タグ or CSS-in-JS | CSS-in-JS or モジュールCSS |

#### 2. ディレクターとして技術選定に関わる

ディレクターの方にとっては、「なぜエンジニアがその技術を選んだのか」を理解できることが重要です。

- クライアントから「WordPressからリニューアルしたい」と言われた → SSG? SSR?
- 「会員制サイトを作りたい」と言われた → SSRが必要になりそう
- 「表示速度を改善したい」と言われた → CSRからSSG/SSRへの移行を検討

#### 3. 実際のプロダクトはハイブリッド

現代のフレームワーク（Next.js、Astroなど）は、**1つのプロジェクト内でSSG・SSR・CSRを混在**させることができます。

```
例：ECサイト
├── トップページ      → SSG（コンテンツは固定）
├── 商品一覧         → SSR（在庫状況をリアルタイム表示）
├── 商品詳細         → SSG + CSR（基本情報はSSG、レビューはCSRで動的取得）
├── カート           → CSR（ユーザー操作に即座に反応）
└── 会社概要         → SSG（ほぼ更新されない）
```

ページの特性に応じて最適な手法を選ぶのが現代のフロントエンド開発です。

## 5. 演習：Astroを使ったSSG

前回紹介したAstroを使って、SSGを体験してみましょう。

### 環境準備

```bash
# Astroプロジェクトを作成
npm create astro@latest my-ssg-site

# プロジェクトに移動
cd my-ssg-site

# 開発サーバーを起動
npm run dev
```

### Astroコンポーネントの基本構造

```astro
---
// フロントマター（サーバーサイド / ビルド時に実行される）
const title = "はじめてのAstro";
const items = ["HTML", "CSS", "JavaScript"];
---

<!-- テンプレート（HTMLとして出力される） -->
<html>
  <head>
    <title>{title}</title>
  </head>
  <body>
    <h1>{title}</h1>
    <ul>
      {items.map(item => <li>{item}</li>)}
    </ul>
  </body>
</html>
```

`---` で囲まれた部分（フロントマター）は **ビルド時に実行** されます。ブラウザには渡りません。

### ビルドしてみる

```bash
# 本番用HTMLを生成
npm run build
```

`dist/` フォルダに完成したHTMLファイルが出力されます。このHTMLを開いてみると、JavaScriptが一切含まれていない、純粋なHTMLファイルであることが分かります。

### 演習課題

1. Astroプロジェクトを作成し、エクセルデータを表示するウェブサイトを作ってみましょう
2. `npm run build` を実行し、`dist/` フォルダの中身を確認してみましょう
3. 生成されたHTMLファイルをブラウザで直接開いてみましょう（サーバー不要で表示できることを確認）

## まとめ

- HTMLレンダリングとは「HTMLを生成する行為」のこと
- HTMLが **いつ・どこで** 生成されるかで、3つの手法に分かれる
  - **SSG**: ビルド時に開発者のPCで生成 → 高速・安全・静的
  - **SSR**: リクエスト時にサーバーで生成 → 動的・最新データ・ユーザー別
  - **CSR**: 実行時にブラウザで生成 → リッチな操作感・SPA向き
- 現代のフレームワークはこれらを **ハイブリッド** に組み合わせる
- マークアップエンジニアは普段からSSGに近いことをしている
