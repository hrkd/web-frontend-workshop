# vol_11: AIコーディングの現在

---

## はじめに

「AIにコードを書いてもらう」というスタイルは、ここ数年でエンジニアの日常になりました。
本稿では、現在主流の AI コーディング環境である **Claude Code** と **Codex** を題材に、それらを使いこなすために知っておきたい基本用語と、実務での使い分けを整理します。

---

対象は「Copilot で補完は使っているけど、エージェント的な使い方はこれから」という方
または、非エンジニアを想定しています。

---

## 0. ここ1年で何が起きたか

体感的に「AI コーディングの空気が変わった」のは、ちょうど1年前くらいからです。

---

- **〜2024年**：GitHub Copilot による「補完」がデファクト。Cursor が台頭し、「チャットしながらコードを書く」スタイルが広がる
- **2025年初頭**：Claude Code がリサーチプレビューとして登場。ターミナルで動くエージェント型 CLI として注目されるが、当初は API 従量課金でヘビーに使うには高くつく
- **2025年5月**：Anthropic が **Max プラン**（高額帯・定額）をローンチ。Claude Code が Max に統合され、まずはヘビーユーザー層から採用が始まる

---

- **2025年6月**：Claude Code が **Pro プラン（$20/月）でも利用可能に**。ここで価格の壁が一気に下がり、個人開発者・現場のエンジニアに普及。「定額エージェント」がデファクトの選択肢になった瞬間
- **2025年後半**：OpenAI が **Codex** を本格投入。ローカルの CLI / IDE / デスクトップアプリと、GitHub に接続したクラウド実行を組み合わせ、PR ベースで並列に複数タスクを走らせるスタイルで対抗

---

- **2025〜2026年**：**MCP** がエコシステムとして広がる。Figma / GitHub / Notion / DB など、エージェントから触れる外部ツールが急増
- **現在（2026年）**：「補完してもらう」から「エージェントに任せる」への移行が進行中。**1日中エージェントを並列で走らせる**ような働き方も珍しくなくなってきた

---

ポイントは、**「$20 帯での定額化」がスイッチだった**ということです。
Max（高額帯）の段階ではまだ一部のヘビーユーザー向けでしたが、Pro で使えるようになった瞬間に「ダメ元で投げて結果を見る」というエージェント前提のワークフローが、ごく普通のエンジニアの選択肢になりました。

---

従量課金だと「無駄打ちが怖い」「とりあえず投げてみる」がやりにくい。月額固定・しかも $20 という価格帯になって初めて、エージェントを"気軽に試せる道具"として扱えるようになった、という構図です。

---

## 1. 基本用語解説

AI コーディングツールの紹介に入る前に、共通言語として押さえておきたい用語を整理します。

---

### LLM（Large Language Model）

大量のテキストデータで学習された大規模言語モデル。
GPT-5、Claude Opus 4.7、Gemini 3 などが該当します。コードもテキストの一種として扱えるため、自然言語の指示からコードを生成できます。

---

### トークン

LLM が文章を扱う最小単位。英語では概ね「単語1つ ≒ 1トークン」、日本語では「ひらがな1文字 ≒ 1〜2トークン」程度の感覚です。
料金やコンテキスト長は基本的にこのトークン数で計算されます。

---

### コンテキストウィンドウ

LLM が一度に処理できるテキストの長さ。
2026年現在は 20万〜100万トークン規模が主流。
このウィンドウに「システムプロンプト・会話履歴・ファイル内容・ツールの実行結果」が全部詰め込まれます。

---

> 💡 ウィンドウが大きいから何でも入れていい、というわけではなく、入れすぎると応答品質が下がる（"context rot"）ため、必要な情報だけを渡す設計が重要です。

---

### エージェント（Agent）

「指示を受け取って自律的にタスクを進める LLM」のこと。
単にチャットで応答するだけでなく、**外部のコマンドや API を呼び出し**、その結果を見て次の行動を決めることができます。

---

「ファイルを読む」「`npm install` を実行する」「Web を検索する」といった動作はすべて、LLM がツールを呼び出すことで実現されています（この仕組みを `Function Calling` / `Tool Use` などと呼びます）。

---

### MCP（Model Context Protocol）

Anthropic が提唱した、LLM と外部ツール／データソースをつなぐ標準プロトコル。
「Figma の情報を取る」「GitHub の PR を見る」「Notion を読む」などを、共通インターフェースで AI に渡せます。
Claude Code / Codex / Cursor などが対応しており、自前の MCP サーバーを書くこともできます。

---

### サブエージェント / 並列実行

メインのエージェントが、特定のタスクを別の専門エージェントに任せる仕組み。
「コードレビュー専門」「リサーチ専門」「テスト作成専門」のように分業させ、独立したコンテキストで並列実行することで、メインの文脈を汚さずに作業できます。

---

## 2. Claude Code と Codex に共通する特徴

Claude Code と Codex は提供元や細かな操作感は違いますが、どちらも「チャットでコードを出してもらう道具」というより、**リポジトリの中で一緒に作業するエージェント**です。

共通する特徴を先に押さえると、個別ツールの違いも見えやすくなります。

---

- **複数の入口がある**：ターミナル、IDE 拡張、デスクトップアプリなど、普段の作業環境に合わせて使える
- **プロジェクトの文脈を読む**：ファイル構成、既存コード、README やプロジェクトルールを読みながら作業する
- **設定やルールを共有しやすい**：プロジェクト単位の指示書、個人設定、MCP 設定などを用意して、複数の入口から同じ前提で動かしやすい
- **ファイルを直接編集する**：提案だけでなく、エージェント自身が複数ファイルをまたいで変更を入れる

---

- **コマンドを実行して確認する**：`npm test`、`npm run lint`、`git diff` などを実行し、結果を見て次の修正に進む
- **外部ツールにつなげられる**：MCP などを通じて、Figma、GitHub、Notion、ブラウザ、DB などの情報を扱える
- **長めのタスクを任せられる**：単発の補完ではなく、「調査 → 実装 → 検証 → 修正」まで一連の流れを任せやすい
- **既存コードベースの改修に強い**：機能追加、リファクタ、型変更の追従、テスト修正など、複数ファイルにまたがる作業を任せやすい

---

つまり、どちらを使う場合でも大事なのは、**AI にコードを書かせることそのものより、AI が動きやすい作業単位・検証方法・レビュー観点を渡すこと**です。

---

## 3. Claude Code

Anthropic 公式のコーディングエージェントです。
もともとはターミナルで使う CLI として広まりましたが、現在は **ターミナル・IDE 拡張・デスクトップアプリ・Web** から扱えます。

---

### Claude Code らしさ

- **ターミナル中心の体験から広がった**：CLI としての使い勝手が強く、開発者が普段使うシェルの中で作業しやすい
- **Claude の推論力をそのまま開発作業に使える**：既存コードの読み解き、仕様の曖昧さの整理、長めの実装相談と相性が良い
- **デスクトップアプリからも扱える**：IDE やターミナルの外で Claude Code のセッションを動かし、複数セッションを並べて進めたりできる

---

### Skills / Hooks / MCP

Claude Code を「自分用」にカスタマイズする3つの仕組み：

| 機能 | 役割 |
|---|---|
| **Skills** | 「このタスクのときはこの手順で」というプレイブック。スラッシュコマンドで呼び出す。 |
| **Hooks** | ツール実行の前後にスクリプトを差し込む。例: ファイル保存後に自動 lint。 |
| **MCP** | 外部ツール／サービスへの接続口。Figma、GitHub、Notion など。 |

---

### 使いどころの感覚

Claude Code は、ターミナルでエージェントと対話しながら、手元のリポジトリをじっくり読ませて進める使い方と相性が良いです。
「まず調べて」「この設計どう思う？」「この方針で実装まで進めて」のように、相談と実装を行き来しながら進める場面で使いやすい、という感覚です。

---

## 4. Codex

OpenAI 公式のコーディングエージェント。
かつての「Codex」（GitHub Copilot の前身モデル）とは別物で、現在は **デスクトップアプリ・CLI・IDE 拡張・Web / Cloud** を横断する製品群です。ローカルの作業ディレクトリで動かすことも、GitHub と接続したクラウド環境にタスクを投げることもできます。

---

### 触れる窓口

- **Codex デスクトップアプリ**：エージェントとのやり取りや差分レビューを扱う専用 UI（macOS / Windows）
- **Codex CLI**：ターミナルで動くローカル実行版（macOS / Windows / Linux）
- **Codex IDE 拡張**：VS Code / Cursor / Windsurf などの VS Code 互換エディタや JetBrains 系 IDE に組み込める
- **Codex Web / Cloud**：GitHub リポジトリに接続し、クラウド環境でタスクを実行して PR まで進められる

---

### Codex らしさ

- **エディタ統合の選択肢が広い**：VS Code 系だけでなく JetBrains にも対応しており、普段のエディタにそのまま入れられる
- **ローカルとクラウドを行き来できる**：手元の作業ディレクトリで一緒に進めることも、重めのタスクをクラウドに任せることもできる
- **差分レビューの体験が強い**：AI が書いたコードを diff で確認し、受け入れる・戻す・コメントして追加修正させる流れが作りやすい
- **Web / Cloud と GitHub 連携が強い**：GitHub リポジトリに接続し、クラウド環境で実装から PR 作成まで進める導線が用意されている

---

### デスクトップアプリでできること

デスクトップアプリは、CLI の GUI 版というより、複数スレッド・Git・worktree・レビュー・自動化をまとめて扱う作業 UI です。

---

- エージェントが書き換えた内容を **差分単位で確認 → 受け入れ／却下** できる（このレビュー周りは触ってみると素直に便利）
- commit / push / PR 作成など、よく使う Git 操作をアプリ内で扱える
- **git worktree** にも対応しており、タスクごとに作業環境を分離できる
- Local / Worktree / Cloud を選び、手元で動かすか、分離した作業場所で動かすか、クラウドに任せるかを切り替えられる
- 統合ターミナルや in-app browser を使って、実行結果や画面の確認まで同じ UI で進められる

---

ターミナル CLI で完結できる作業も多いですが、複数タスクを並列に走らせたり、差分レビューや Git 操作を画面上で追いたい場合はデスクトップアプリが便利です。

---

## 5. 実務での活用例

ツールの選択を抜きにして、AI エージェントを業務のどこに差し込めるかを整理します。

---

### 設計・調査での使い方

対話的にエージェントとやり取りしながら進めるパターン。

- 既存コードの構造を読み解いてもらう
- 「この機能を入れるにはどのファイルを触る？」を相談する
- 仕様の曖昧さを質問してもらって明文化する

---

### 反復・量産タスクでの使い方

ある程度仕様が固まっているタスクをまとめて任せるパターン。

- 同じ型変更を複数ファイルに展開する
- Lint エラーをまとめて潰す
- ドキュメント更新・i18n キーの一括追加

---

### マークアップ・フロントエンド業務での例

- **Figma → コード**：MCP 経由で Figma のデザインデータをエージェントに渡し、コンポーネントを生成
- **アクセシビリティ確認**：エージェントに WAI-ARIA の観点でレビューさせる
- **ライブラリ調査**：「この用途で React の良いライブラリ調べて、最小サンプルまで作って」を投げる

---

### ディレクター業務での例

- 仕様書・要件定義のレビュー（エンジニア視点での突っ込み）
- 見積もりのための工数感ヒアリング
- 過去 PR を読ませて「このリポジトリで最近どんな変更が入った？」を要約

---

## 6. マシンリーダブルなドキュメントの重要性

エージェント時代になって急に重要度が上がったものがあります。それが **Markdown** をはじめとする「マシンリーダブルなドキュメント」です。

---

Claude Code も Codex も、タスクを進めるうえでプロジェクト内の文書を重要な手がかりにします。
そのとき参照されやすく、指示として効きやすいのが、`README.md` / `CLAUDE.md` / `AGENTS.md` / `docs/*.md` といった **Markdown 文書**です。

---

- 指示書（`CLAUDE.md` などのプロジェクトルール）
- 仕様書（PRD、設計ドキュメント）
- スキル定義（`SKILL.md`）
- API リファレンス

これらが「人間に読みやすいか」だけでなく、**「AI に読みやすいか」** で品質が決まる時代になりました。

---

### なぜ Markdown なのか

Markdown が選ばれている理由は、HTML が Web のセマンティクスを担っているのと同じ理屈ですが、さらに **「プレーンテキストでありながら構造を持つ」** という性質が強力です。

---

- LLM のコンテキストに入れたときに、トークン効率が良い
- 見出し（`#`）で章立てが伝わり、AI が「目次として把握→必要な節だけ読む」ができる
- コードブロックの言語指定（` ```ts `）で、AI がパース戦略を切り替えられる
- 差分（diff）が綺麗に出るので、AI が編集した結果のレビューがしやすい

---

### 「マシンリーダブル」の重要性

ここで言う **マシンリーダブル** = 機械が**意味を取り違えずに**読める、ということです。

---

悪い例：
```
■概要
このAPIは、ユーザー情報を取得するためのものです。
パラメータ：id（必須）、format（任意、デフォルトはjson）
返り値：ユーザーオブジェクト
```

---

良い例：
```markdown
## 概要

ユーザー情報を取得する API。

### パラメータ

| 名前 | 型 | 必須 | 説明 |
|---|---|---|---|
| `id` | string | ✓ | ユーザー ID |
| `format` | `"json"` \| `"xml"` |  | デフォルト: `json` |

### 返り値

`User` オブジェクト（[型定義](./types.md#user)）
```

---

後者は、人間にとってもAIにとっても **「ここに何が書かれているか」が構造から分かる**。
これは、HTML で `<table>` を正しく書くのと本質的に同じ営みで、vol_2 で扱ったアクセシビリティと同じ考えがそのまま適用できます。

---

### 実務での所作

- プロジェクトルートに `CLAUDE.md` / `AGENTS.md` を置き、ルール・前提・避けるべきことを明記する
- 設計ドキュメントは Notion ではなく Markdown で書き、リポジトリに含める（AI が読める場所に置く）
- コードコメントよりも、近接するドキュメントで補足する（LLM はドキュメントの方が文脈を取りやすい）

---

## まとめ

- AI コーディングは「補完」から「エージェント」のフェーズに移っている
- 転換点は **2025年6月、Claude Code が Pro プラン（$20/月）で使えるようになったこと**。「ダメ元で投げる」が現実的になった
- 用語（LLM / トークン / コンテキスト / ツール / MCP / サブエージェント）を押さえると、各ツールの設計思想が読めるようになる

---

- Claude Code も Codex も、ターミナルだけでなく IDE やデスクトップアプリから扱える。Codex はさらに Web・Cloud で GitHub 連携タスクを走らせる入口もあるため、使い慣れた環境や、ローカルで進めたいかクラウドに任せたいかで選べばよい
- **マシンリーダブルなドキュメント（Markdown）の重要性が再燃**。マークアップの意味づけスキルは、AI 時代のドキュメンテーションにそのまま活きる
- 自分の業務フローのどこに差し込めるかを意識して触ってみる

---

「触ってみる」が一番の近道なので、まずは小さなリポジトリで1タスク任せてみるところから始めてみてください。
