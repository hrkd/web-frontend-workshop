# WebGL シェーダー芸入門 — GLSL で「画」を作る

vol_09 では three.js（スリージェイエス）の登場人物（シーン／カメラ／メッシュ／レンダラー）を組み合わせて 3D 空間を描きました。今回は、その描画パイプラインの **シェーダー** ─ ピクセルや頂点を「実際に計算している部分」 ─ を説明していきます。

「画面のピクセル1つ1つに対して、好きな色を計算式で出力できる」。これが分かると、いままで使ってきた three.js のマテリアルが「他人が書いたシェーダーをロードしていただけ」だったと見えてきます。そして自分でシェーダーを書けると、表現の幅が一段違う場所まで広がります。

本編は **「絵を見て、それがどんなステップで描かれているか」だけを駆け足で追う構成** にしています。GLSL の文法や three.js のお作法といった基礎は本編では深く触れず、付録としてまとめてあります。コード本体は demo（`vol_10/demo/`）でブラウザから直接読めるので、深掘りはそちらで。

## 2. パターン1：vertex shader で図形を歪ませる

### 完成イメージ

![パターン1：図形を歪ませる](./screenshots/pattern1.png)

普通の球体（sphere／スフィア）を置いたのに、光が当たって陰影もちゃんと出たまま、表面がうにょうにょ動く。**形そのものをアニメーションさせている** 状態です。

### 描画のステップ

1. **球を細かく分割した普通のメッシュを置く**（`SphereGeometry` + `MeshStandardMaterial`）。ライト・影・反射は three.js のマテリアルに任せる
2. **頂点の位置を時間で動かす**：各頂点を、その座標と時間に応じて法線方向（=表面の外向き）に押し出す
3. **既存マテリアルのシェーダーをパッチする**：`onBeforeCompile`という仕掛けで、`MeshStandardMaterial` 内部の vertex shader にある「ここで頂点位置を作るよ」というマーカー（`#include <begin_vertex>`）に割り込み、自分の押し出し式を差し込む

実装は demo の `vol_10/demo/vertex_distort.html` に。右下に表示される白黒の球面マップは、**球面上の各点で「いまどれだけ押し出されているか」** を緯度経度に展開して見せたもので、本体の球と同時に動くので波の形と動きの関係が直感できます。

### 学べるポイント

- **形そのものをアニメーションさせるには vertex shader を触る**
- 全部捨てて自分で書き直すのではなく、**`onBeforeCompile` で頂点の計算だけ差し替える** のが実用的な戦略
- ライト・影・反射は three.js のマテリアルが面倒を見てくれるので、注力できるのは「**形をどう動かすか**」だけ

## 3. パターン2：パーティクル（particle／粒子）

### 完成イメージ

![パターン2：パーティクル](./screenshots/pattern2.png)

何万個もの光点が漂う背景。それぞれの粒が少しずつ違うタイミング・方向で動き、全体としてうねりのある流体のように見える。点が重なった部分はより明るく光る。

### 描画のステップ

1. **3万個の頂点位置を JS で生成**：`BufferGeometry`（バッファジオメトリ）という箱に、`Float32Array`（数値の配列）を直接流し込む。「点1個 = 頂点1個」のイメージ
2. **`THREE.Points`（ポインツ）で「点として描く」モードに**：通常の `THREE.Mesh` は「頂点で三角形を作って塗りつぶす」描画だが、`Points` は「頂点をそのまま点として描く」。これだけで万単位の描画が現実的になる
3. **vertex shader で各点を動かす**：各頂点の位置に時間を絡めた式を加えて、ふわふわ揺らす。**CPU で `for` ループは回さない**（全部 GPU 並列）
4. **fragment shader で粒の見た目を決める**：四角い点を円形にくり抜き、ふちをふわっとぼかし、**加算合成**（重なるほど明るくなる）で光感を作る

実装は demo の `vol_10/demo/particles.html` に。

### 学べるポイント

- **大量の点は `Points` + `BufferGeometry`**。これだけで万単位の描画が現実的になる
- 各粒の挙動は **vertex shader 側に書く**。CPU でループを回さない、というのが GPU パワーの活かし方
- 加算合成にすると、点が重なった場所が明るくなり、星屑・煙・光跡といった光の演出に向く

## 4. パターン3：ポストプロセス（post process／後処理）

### 完成イメージ

![パターン3：ポストプロセス](./screenshots/pattern3.png)

vol_09 で作った **鳥瞰ビューの街** に、画面端ほど強くなる **色収差** と、四隅を暗く落とす **ビネット** を後処理で重ねる。建物の輪郭に RGB のズレが出て、レンズで覗いたようなレトロな質感に変わる。

### 描画のステップ

ポストプロセスの本質は、**「一旦シーンを画像（テクスチャ）に焼いて、その画像にもう一度シェーダーをかける」** という二段構造です。

```
[シーン描画] → [画像（テクスチャ）] → [ポストシェーダー] → [画面]
```

1. **シーンを画像に焼く**（`RenderPass`／レンダーパス）：vol_09 の街シーンをそのまま使う
2. **色収差をかける**（自作 `ShaderPass`／シェーダーパス）：R / G / B のチャンネルを画面端ほど大きく外側にズラして取り出す → 輪郭に色が滲む
3. **ビネットを重ねる**（自作 `ShaderPass`）：画面中央から四隅に向かって暗く落とす

パスを順番に **`EffectComposer`** に積むだけで、前のパスの結果が次のパスの入力に自動で繋がります（前段の画像は `uniform sampler2D tDiffuse` に勝手に入ってきます）。

実装は demo の `vol_10/demo/post_process.html` に。

### 学べるポイント

- **「画面全体に効果をかけたい」要望のほとんどはポストプロセスで解ける**
- 各 `ShaderPass` の中身は結局 **「画面いっぱいの板1枚 + fragment shader」**。後で扱うパターン4と同じベースの仕組み
- パスを足し算するだけでエフェクトを重ねられる。**1つ1つは小さな fragment shader** で済むので、自作のハードルが低い

## 5. パターン4：フラグメントシェーダーで「一枚絵」を描く（3D メタボール）

### 完成イメージ

![パターン4：一枚絵](./screenshots/pattern4.png)

画面いっぱいの板1枚と fragment shader だけで、複数の球がぬるっと融合する **3D メタボール** を描いています。three.js のシーンに置いてあるのは「板1枚」だけ。**3D のように見える絵を、fragment shader が全部計算で作っている** という状態です。

右下の小窓は、本体の絵を作るためにシェーダー内部で何が起きているかを **ステップごとに分解** した補助画面。本文の解説はこの4パネルに沿って進めます。

### 触りだけ：レイマーチング + SDF の世界観

ここで使っているのは **レイマーチング（ray marching）＋ SDF（Signed Distance Function／符号付き距離関数）** という、vol_09 のメッシュベース3DCGとはまったく別世界のテクニックです。深掘りすれば1冊の本になるので、ここではコードを読み込まずに **流れだけ** を追います。

```
ステップ1：4つの中心が動く     → center trails パネル
ステップ2：そこから場が作られる → SDF (z=0) パネル
ステップ3：視線で場をなぞる     → depth パネル
ステップ4：陰影で色を作る       → diffuse パネル
```

実装は demo の `vol_10/demo/fragment_canvas.html` に。

### ステップ1：4つの中心が動く（center trails）

3D 空間に4個の「**力の中心**」を置き、時間 `t` から `sin` / `cos` で動かすステートレスな関数。各中心は違う周波数・位相で動かしているので、互いに違う軌跡を描きます。

**`center trails` パネル**：4個の中心の現在位置と、過去2秒分の残像を色分けで描いたもの。**「世界が時間で変わる」起点**。

### ステップ2：4つの中心から「場」を作る（SDF）

3D 空間のあらゆる点 `p` について **「物体表面までの最短距離」** を返す関数を作ります。これが **SDF（距離関数）** で、「**3D 空間全体に広がるスカラーの場**」だと思って構いません。

- 1個の球：`length(p - 中心) - 半径`
- 4個の球：それぞれの距離を、**滑らかな最小値（smin／スムーズ・ミニマム）** で1つに合成。`smin` の `k` は「**糊しろの広さ／粘度**」を決める値

ここで重要なのは、**「物体の表面（=膜）」を頂点や三角形として作っているわけではない** こと。**関数だけ** が存在し、表面は「場の値が 0 になる場所」として暗黙的にそこにある、という世界観です。

**`SDF (z=0)` パネル**：3D の場を z=0 平面で輪切りにして色マップしたもの。**赤=内側、青=外側**。

### ステップ3：視線で場をなぞる（depth）

各ピクセルは「カメラから自分のピクセル位置に対応する方向に視線レイを飛ばす」役目を持ちます。そのレイを SDF を頼りに前進させて物体の表面を見つけるのが **レイマーチング**：

1. 現在位置で「場の値（=最も近い表面までの距離）」を聞く
2. **その距離ぶんだけ** 前に進む（その距離内には絶対に表面がない、と保証されている）
3. 場の値が十分小さくなったら「**ヒット**」とみなして停止
4. 進みすぎたら（=箱庭の外）諦めて停止

これを for ループで繰り返すだけ。**ループそのものがマーチング**。

**`depth` パネル**：各ピクセルでヒットまでの距離 `t` を白黒で表したもの。**手前=白、奥=黒**。膜を事前に持っていないのに、画面のどのピクセルもちゃんと「最初に当たる表面の点」を見つけている。

### ステップ4：ヒット位置で陰影を計算（diffuse）

ヒットした地点で、SDF を **そのまわりで少しずつずらしてサンプル** すると、場の **勾配（gradient）** が得られます。これがそのまま **表面の法線（normal）**。

法線が得られれば、あとは普通の3DCGと同じく **ライト方向との内積** を取れば、**拡散光（diffuse）** による陰影が出ます。

**`diffuse` パネル**：上の計算結果をそのまま白黒で描いたもの。**本体の最終出力もこの式そのもの**（本体は全画面、パネルは縮小版）。

### 学べるポイント

- **物体を「メッシュ」ではなく「距離関数」として持つ世界観**：vol_09 の3DCGとは別ラインの考え方
- **「膜」を事前に作らず、各ピクセルが独立に発見する**：GPU の並列性をフル活用
- **「fragment shader + ループ + 距離関数」** という小さな道具立てで、3D メタボール／フラクタル／ボリュームレンダリングなど、表現の幅が一気に広がる

## 付録：シェーダーの基礎知識

本編で深く解説せずに使った用語を、参照用にまとめています。

### 付録1. vertex shader と fragment shader

GPU で描画される 1 枚の絵は、必ず2種類のシェーダーを順番に通ります。

#### 全体の流れ

`renderer.render(scene, camera)` を呼ぶと、three.js は **シーン内のメッシュごとに「描画命令（draw call／ドローコール）」を1回ずつ発行** します。1つの draw call の中で起きていることは以下：

```
シーン内の各メッシュについて 順番に：
┌─────────── 1つの draw call ───────────┐
│                                          │
│ [ JS ]                                    │
│    │ attribute（アトリビュート）             │
│    │   そのメッシュの頂点ごとに違うデータ      │
│    │ uniform（ユニフォーム）                │
│    │   そのメッシュの全頂点・全ピクセル共通    │
│    ↓                                      │
│ [ vertex shader ] 頂点1個ずつに走る         │
│    │  出力は gl_Position（画面上の頂点位置）  │
│    │ varying（バリイング）                  │
│    │   vertex → fragment へバケツリレー     │
│    ↓                                      │
│ [ ラスタライズ（rasterize） ]               │
│    ① 3頂点をつなぐと三角形が1枚できる         │
│    ② その三角形が画面のどのピクセル群を        │
│       覆っているかを、GPU が自動で判定         │
│    ③ 覆われた各ピクセルに対して fragment     │
│       shader が呼ばれる                    │
│    ④ そのピクセルで使う varying は、         │
│       「3頂点の値をピクセル位置に応じた重みで   │
│       混ぜた補間値」が自動で入る              │
│    ↓                                      │
│ [ fragment shader ] ピクセル1個ずつに走る    │
│    出力は gl_FragColor（=そのピクセルの色）   │
│                                           │
└───────────────────────────────────────────┘
   ↓ 次のメッシュへ（draw call をもう1回）

全メッシュの draw call が完了
   ↓
[ 画面 ]
```

つまり「**メッシュごとに順番（シリアル）**、**1つの draw call の中だけ並列**」という二段構え：

- **外側のループ**：シーン内のメッシュ数ぶん draw call が発行される
- **内側の処理**：1つの draw call の中で vertex shader と fragment shader が GPU で並列実行

頂点が10万個あれば **vertex shader（バーテックスシェーダー／頂点シェーダー）** は10万回、画面が 1920×1080 なら **fragment shader（フラグメントシェーダー／断片シェーダー）** は約207万回、**それぞれ完全に並列で** 走ります（これは1つの draw call の中の話）。

なお、メッシュ数が増える＝draw call の回数が増えるので、シーン内のメッシュ数が数千個を超えると描画速度が落ちます。パターン2のパーティクルが **3万個の点を1つの `Points` メッシュ＝1 draw call** にまとめているのは、まさにこの最適化のためです。

#### 「ピクセル位置に応じた重みで混ぜた補間値」とは

ラスタライズの ④ で出てきた **「補間値」** が分かりにくいので、具体例で噛み砕きます。要は「**ピクセルが近い頂点ほど、その頂点の値を強く反映する**」という、ただの距離の重み付き平均です。

**1次元（線分）の例**：

```
A ●────────●────────● B
  赤       ?       青
```

点 A で「赤」、点 B で「青」と決まっているとき、

- **A の真上** のピクセル → A:100%, B:0% → 純粋な赤
- **A と B のちょうど真ん中** → A:50%, B:50% → 赤と青を半々で混ぜた紫
- **A から 3/4 進んだ位置**（B 寄り）→ A:25%, B:75% → 青寄りの紫

これが「**位置に応じた重みで混ぜる**」の意味。

**2次元（三角形）の場合**：

3頂点 A=赤、B=緑、C=青の三角形があるとき、各ピクセルの位置に応じて A・B・C の影響度（合計100%）が決まります。

| ピクセルの位置 | A | B | C | 結果の色 |
| --- | --- | --- | --- | --- |
| 頂点 A の真上 | 100% | 0% | 0% | 純粋な赤 |
| 辺 AB の中点 | 50% | 50% | 0% | 赤と緑の中間（黄色っぽい） |
| 三角形のど真ん中（重心） | 33% | 33% | 33% | 3色を均等に混ぜた色 |
| 頂点 C 寄りの内部 | 10% | 10% | 80% | ほぼ青 |

GPU はラスタライズの段階で **「このピクセルから見て3頂点はどの比率か」** を全ピクセルぶん自動で計算し、その比率を使って3頂点の varying（色・法線・UV など）を混ぜて、fragment shader に渡してくれます。プログラマがやることは「**vertex 側で頂点ごとに値を varying に詰める**」だけ。

数学的にはこれを **バリー中心座標（barycentric coordinates／重心座標）** による線形補間と呼びますが、感覚としては **「近い頂点ほど強く効く距離の重み」** だと思っておけば十分です。

#### vertex shader は何を計算するか

入力された頂点座標 `position`（3D 空間上の点）を、**画面上のどこに置くか** の座標に変換します。出力先は組み込み変数 **`gl_Position`（ジーエル・ポジション）**。

three.js は、変換に必要なカメラ行列を `uniform` として自動で渡してくれているので、最小の vertex shader は次の1行で済みます：

```glsl
gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
```

- `position`：頂点の3D 座標（`attribute`、頂点ごとに違う）
- `modelViewMatrix`（モデルビューマトリックス） / `projectionMatrix`（プロジェクションマトリックス）：「物体の置き場所 + カメラ視点 + 投影」を表す行列（`uniform`、全頂点で共通）

この行列を掛け算するだけで、3D の点が **クリップ空間（clip space／クリップスペース）**（画面のどこに映るかが −1〜1 で表される世界）の座標になります。

#### fragment shader は何を計算するか

ラスタライズで「このピクセルはこの三角形の中だよ」と分かったあと、**そのピクセルを何色にするか** を自分で計算し、結果を組み込み変数 **`gl_FragColor`（ジーエル・フラグカラー）** に代入します。

ここで `gl_FragColor` は「**画面のこのピクセルに、最終的にこの色を映してね**」という出力スロットでしかありません。**色そのものをどう作るかは、`main` 関数の中の計算式（=プログラマが自分で書く GLSL のコード）が決めます**。形式は `vec4(R, G, B, A)`（R/G/B/A は 0.0〜1.0）。

イメージとして、いくつか書き方の例：

```glsl
// 例1：固定値で塗る（このピクセル＝赤）
gl_FragColor = vec4(1.0, 0.0, 0.0, 1.0);

// 例2：varying（UV 座標）に応じて色を変える ─ uv が変わるとピクセルごとに違う色
gl_FragColor = vec4(vUv.x, vUv.y, 0.5, 1.0);

// 例3：テクスチャ画像から色を取り出す
gl_FragColor = texture2D(tex, vUv);

// 例4：好きな数式で計算してから入れる（パターン4はこの形）
float d = length(vUv - vec2(0.5));
gl_FragColor = vec4(vec3(1.0 - d), 1.0);
```

つまり、

- `gl_FragColor` は **「色を入れる箱」**
- **中身の色は、`main` 関数の中で自分で書いた計算式の結果**
- vertex shader から渡される `varying`（uv や頂点色など）や、JS から渡される `uniform`（時間、解像度、テクスチャなど）を計算式に組み込むことで、**ピクセルごとに違う色** や **時間で変わる色** が作れる

これが「fragment shader で絵を描く」の正体です。

#### 最小の例

```glsl
// --- vertex shader ---
varying vec2 vUv;                                                  // fragment に渡す箱
void main() {
  vUv = uv;                                                         // attribute → varying に詰める
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
}

// --- fragment shader ---
varying vec2 vUv;                                                  // vertex 側と同じ宣言
void main() {
  gl_FragColor = vec4(vUv.x, vUv.y, 0.5, 1.0);                     // u, v をそのまま R, G に
}
```

これだけで、メッシュ表面が **左下=黒、右上=黄色** に滑らかにグラデーションする絵が出ます。`vUv` が頂点間で補間されているので、コードは2行ずつなのに、ピクセル単位の滑らかな色変化が手に入る、というのが GPU 描画の効きどころです。

#### 主な varying の使い道

vertex 側で何を varying に詰めるかは、fragment 側で何を計算したいか次第。代表的なものを並べておきます。

| 使い道                         | varying の宣言例              | 何のために                                                  |
| ---------------------------- | ----------------------- | ----------------------------------------------------- |
| **テクスチャを貼る**                 | `varying vec2 vUv;`     | fragment 側で `texture2D(tex, vUv)` を使うため                |
| **ライティング**（陰影を出す）            | `varying vec3 vNormal;` | 法線とライト方向の内積で明るさを計算するため                                |
| **頂点ごとに違う色**                 | `varying vec3 vColor;`  | 頂点で計算した色を fragment に伝える                                |
| **距離フォグ / 影 / 反射**           | `varying vec3 vWorldPos;` | ワールド空間でのピクセル位置を使って、霧の濃さや反射方向を計算する               |
| **頂点で計算したカスタム値**             | `varying float vWave;` 等 | 頂点ごとに出した「波の高さ」「ダメージ量」「温度」などを fragment 側で参照する |

要は **「vertex で計算した値を fragment 側でも使いたい」** と思ったら、すべて varying。

#### 法線（normal）は既製マテリアル使用時は自動

`MeshStandardMaterial` / `MeshLambertMaterial` / `MeshPhongMaterial` などの **three.js の既製マテリアル** を使うときは、**法線の varying 渡し → ライト方向との内積 → 陰影計算** の一連が内部で全部済んでいます。プログラマが `normal` や `vNormal` を直接書くことはありません。

法線を自分で扱う必要があるのは、おもに：

- **`ShaderMaterial` で vertex / fragment を両方自分で書く** とき
   → `normal` そのものは three.js が `attribute` として自動で渡してくれている（付録3 参照）ので、自分で attribute を宣言する必要はない。プログラマが書くのは「**それを fragment に届ける varying のバケツリレー**」だけ：
   `varying vec3 vNormal;` を宣言し、vertex 側で `vNormal = normalMatrix * normal;` と詰める
- **`onBeforeCompile` で既製マテリアルの一部を差し替える** が、法線まわりも差し替えたい とき（=レアケース）

普段の three.js は「**法線の存在を意識しなくても、勝手にライトが効いている**」状態。自分でゼロからシェーダーを書くときに初めて、`normalMatrix * normal` → `varying` → `normalize` というお作法を意識します。

### 付録2. attribute / uniform / varying

シェーダーが受け取れる値は、出どころによって3種類に分かれます。

| 種類          | 読み方     | どこから来る                | 例                                   |
| ----------- | ------- | --------------------- | ----------------------------------- |
| `attribute` | アトリビュート | 頂点ごとに違うデータ            | 頂点座標 `position`、法線 `normal`、UV `uv` |
| `uniform`   | ユニフォーム  | JS から、全頂点・全ピクセルで共通の値  | 時間 `u_time`、解像度 `u_resolution`、行列   |
| `varying`   | バリイング   | vertex → fragment へ送る | UV 座標、頂点色など                         |

「`attribute` は頂点ごと」「`uniform` は全部共通」「`varying` は vertex から fragment へのバケツリレー」と覚えておけば十分です。

### 付録3. three.js が裏で渡してくれているもの

three.js の **`ShaderMaterial`（シェーダーマテリアル）** を使うと、毎回書く定型の `uniform`（ユニフォーム）や `attribute`（アトリビュート）は自動で挿入されます。

**`attribute` として宣言済み**：

- `position`（頂点座標 vec3）
- `normal`（法線 vec3）
- `uv`（UV 座標 vec2）

**`uniform` として宣言済み**（カメラ系）：

- `modelMatrix`（モデルマトリックス mat4）
- `viewMatrix`（ビューマトリックス mat4）
- `modelViewMatrix`（モデルビューマトリックス mat4）
- `projectionMatrix`（プロジェクションマトリックス mat4）
- `normalMatrix`（法線変換用 mat3）
- `cameraPosition`（カメラの位置 vec3）

なので vertex shader 内で `normal` や `projectionMatrix` などと書けば、それぞれ値が入った状態で使えます。「**自分で attribute / uniform を宣言する必要はない**」のがこの自動挿入のありがたさです。

完全に手書きしたい（=自動挿入を一切なしにしたい）特殊なケースでは、`RawShaderMaterial`（ロー・シェーダーマテリアル）という別物を使います。

### 付録4. UV 座標（ユーブイざひょう）

「**物体の表面に画像を貼るための2D の地図**」のような座標。3D の頂点座標 `(x, y, z)` と区別するため、アルファベットの末尾から `(u, v)` の2文字を当てた慣習的な名前。

- 範囲は **0.0〜1.0**（左下 = `(0, 0)`、右上 = `(1, 1)`、中央 = `(0.5, 0.5)`）
- 物体の各頂点が「テクスチャのどの場所に対応するか」を `(u, v)` の値として持つ
- fragment shader 側では、ピクセルごとに **頂点間で補間された `uv`** が降ってくる
- 板1枚を全画面に貼って絵を作るときは、**`gl_FragCoord`（ジーエル・フラグコード／ピクセル単位の絶対座標）** を解像度で割って **自前で uv を作る** こともある（パターン4で使う方式）

使い道：① **`texture2D(tex, vUv)`（テクスチャ・ツーディー）** で画像から色を取る、② `uv` を数式に入れて絵を計算で作る。

## 6. 課題

各 demo を開き、シェーダーの数値を変えて見え方の変化を観察してみてください。

- **パターン1**：`onBeforeCompile` の中の波の式の周波数・振幅を変える。複数方向の波を重ねる（`sin(x) + sin(y)`）
- **パターン2**：粒の数・色・サイズを変える。マウス座標を uniform で渡して「マウスに近い粒を弾く」インタラクションも面白い
- **パターン3**：色収差の量、ビネットの強さを変える。3つ目の `ShaderPass`（ノイズ・モノクロ・グリッドなど）を追加する
- **パターン4**：`scene` 関数の `smin` の `k` 値（粘度）、球の半径、中心の動きの周波数を変える。**4パネルがどう変わるかを観察する** のが一番効きます

さらに余裕があれば [Shadertoy](https://www.shadertoy.com/) でお気に入りの fragment shader を写経してみるのも非常に有効。

## 7. まとめ

- **画は fragment shader だけで作れる**。形は頂点ではなく **距離関数や数式** として持つこともできる
- **vertex shader を触れば形そのものをアニメーションできる**。`onBeforeCompile` で既存マテリアルの一部だけ差し替えるのが実用的
- **大量の粒は `Points` + `BufferGeometry`**。挙動は CPU でなく vertex shader 側に書く
- **画面全体に効果をかけたいときはポストプロセス**。`ShaderPass` を積むだけでエフェクトを重ねられる
- 4パターンとも、結局は **「vertex shader / fragment shader / uniform でデータを渡す」** の使い分けだけで成り立っている。覚える語彙は少ない
